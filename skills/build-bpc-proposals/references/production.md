## Authoring and navigation

Use approved native text and canonical calculated tables. Asset paths in project JSON resolve relative to that file. Build with `studio.py build INPUT.json --output OUTPUT.docx`. Tables use native editable cells, deliberate widths, repeating headers, flexible row heights, visible light borders, unit headers and appropriate numerical alignment. Charts retain data, TeX, vector PDF and placement PNG.

Assign stable body and appendix IDs. Put a body call beside the claim it supports; the appendix index links every appendix, and each appendix returns to its relevant section and the index. Printed labels remain useful without clicks. Check semantic destinations as well as link existence.

## Render and inspect

Run `studio.py render OUTPUT.docx --out-dir RENDER`, followed by `studio.py audit OUTPUT.docx --pdf RENDER/OUTPUT.pdf --project INPUT.json --output audit.json`. Inspect every page at readable size: actual fonts, margins, page numbers, section openings, table continuations, captions, labels, figure placement, appendix flow and body count under the real rule. Repair, rerender and reinspect affected flow. A structural audit pass deliberately still requires visual review.

A manual Word export can be the intended final rendering environment; rasterize and inspect that exact export. Font substitution and renderer differences can change pagination. A successful render does not establish economics, research support or live URL access.

Keep private comment identities, machine paths, drafting residue, unsupported claims and tool receipts out of audience files. Preserve editable sources and clean project continuity. A complete proposal does not automatically require a BMC, deck, prototype or validation dossier.
